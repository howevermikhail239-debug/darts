# Часть I. Изменения

## 1. Сервер (`server.mjs`)

Файл переписан в нормальном форматировании: было 74 строки длиной до 617
символов, стало читаемо, с выделенными функциями. Поведение менялось только там,
где указано ниже.

### Порча данных при чтении тела запроса

Было: `body += chunk` внутри `for await`. Каждый чанк декодировался из UTF-8
независимо, поэтому многобайтовый символ, разорванный на границе чанка,
превращался в два `U+FFFD`. Воспроизводилось обычным `fetch` без атаки: сервер
отвечал `201 Created` и записывал испорченные данные на диск. Приложение
русскоязычное, кириллица есть в именах игроков и в `participantNames` каждого
матча.

Стало: чанки собираются в массив и декодируются один раз через `Buffer.concat`.
Лимит 512 КБ по-прежнему считается в байтах и проверяется до конкатенации.

### Отравление keep-alive соединения при отказе по размеру

Было: `throw` изнутри `for await` оставлял тело недочитанным, сокет возвращался
в пул живым, следующий запрос по нему рвался. Это и была причина, по которой
серверные тесты падали в 40–60 % прогонов.

Стало: поток дренируется, соединение помечается на закрытие. Восемь прогонов
подряд без сбоев.

### Ложные конфликты версий

Было: `JSON.stringify(old) !== serialized` — побайтовое сравнение. Одно и то же
тело давало `201`, `409` или `200` в зависимости от того, как сеть нарезала
пакеты. При конфликте синхронизация молча заменяла корректную локальную версию
матча серверной.

Стало: сравнение канонической сериализации с сортировкой ключей на всех уровнях,
плюс явная ревизия и семантика `if-match`. Ревизия хранится рядом с матчем и
наружу в списке `matches` не отдаётся — формат ответа для клиента не изменился.

### Невосстановимая защёлка при сбое хранилища

Было: флаг `storageError` выставлялся при первом неудачном `rename` и не
сбрасывался нигде. После устранения причины API продолжал отдавать `503`
бессрочно; процесс при этом жив, поэтому `Restart=on-failure` не срабатывал, а
статика отдавалась нормально — пользователь видел рабочее приложение, которое
молча перестало синхронизироваться.

Стало: флаг сбрасывается после успешной записи, добавлена периодическая проба
записи для самовосстановления, операции чтения при отказе разрешены.

### Наблюдаемость

Было: единственный `console.log` — строка запуска. Общий `catch` превращал любое
внутреннее исключение в `400 bad_request` и нигде его не фиксировал.

Стало: структурированный лог каждого запроса в stderr с заменой токена на первые
восемь символов его хэша; внутренние ошибки отделены от клиентских и логируются
со стеком; уровень управляется переменной `LOG_LEVEL`.

Логирование на API Gateway остаётся намеренно отключённым — токен находится в
пути URL. Компенсация теперь есть на стороне приложения.

### Стоимость записи и квоты

Было: каждая запись клонировала и сериализовала всю базу целиком. Замеры: при
файле 19,6 МБ один PUT занимал 211 мс против 6,9 мс на пустой базе; RSS
превышал размер JSON примерно в 20 раз, то есть на машине с 1 ГБ памяти потолок
наступал около 40 МБ. При лимите тела 512 КБ и отсутствии ограничений на объём
`confirmedVisits` одна компания достигала этого за 60 запросов.

Стало: клонируется только изменяемая группа. Введены квоты — длина списка
визитов, размер сериализованного матча, число матчей и игроков в группе, общее
число групп. Превышение отдаёт внятный код, а не общий `bad_request`.

### Ограничение частоты и проверка типа содержимого

Было: `POST /api/groups` создавал компании анонимно и без ограничений — 500
групп за 826 мс. Тип содержимого запроса не проверялся, поэтому этот эндпоинт
вызывался кросс-доменно без предварительного запроса CORS.

Стало: ограничитель по адресу из `x-forwarded-for` на создание компаний и на
изменяющие запросы по токену; обязательный `content-type: application/json` на
всех запросах с телом.

### Ключи прототипа в идентификаторах из URL

Было: `target.players['constructor']` возвращало унаследованное значение, оно
проходило проверку на существование, и запись вида `{"constructor": {...}}`
доходила до диска и возвращалась клиенту как игрок без `id` и `name`. Для
`matchId` тот же механизм давал неустранимый `409`.

Стало: проверка собственных свойств во всех местах доступа по ключу из URL плюс
валидация формата идентификатора. Глобального загрязнения прототипа не было и
раньше — это проверялось отдельно.

### Проверка содержимого матча

Было: `validMatch` проверял только верхний уровень. Элементы `players` не
проверялись вовсе, `winnerId` и `participantNames` — тоже.

Стало: проверяется структурная согласованность — элементы `players` непустые и
уникальные, `winnerId` входит в состав, у каждого игрока есть имя, `completedAt`
присутствует у завершённых. Доменные правила игры сервер по-прежнему не
проверяет, это осознанный компромисс, он описан в аудите.

### Прочее по серверу

- Корректное завершение по `SIGTERM` и `SIGINT` с ожиданием записи; удаление
  оставшихся временных файлов при старте.
- Обработчики `unhandledRejection`, `uncaughtException`, `clientError`.
- Таблица MIME по расширению вместо цепочки `endsWith` с запасным вариантом
  `text/html` для любого неизвестного типа.
- Проверка реального пути через `realpath` дополнительно к лексической.
- Заголовки безопасности: `nosniff`, `referrer-policy`, HSTS, `x-frame-options`,
  политика содержимого.
- Таймауты заголовков и запроса, ограничение числа соединений.
- Читается переменная `HOST`, которая была объявлена в юните и не использовалась.

## 2. Правила игры

### Дополнительный круг в серии (`FixedVisitsRules.ts`)

Было: при ничьей после регламента дополнительный круг бросали **все** игроки, а
победитель определялся по накопленной сумме. Воспроизведение: A и B по 60, C
отстал с 20; C бросает 180 и выигрывает матч.

Стало: круг разыгрывают только ничейные игроки, победитель определяется по
очкам круга, при новом равенстве следующий круг — между лидерами этого круга.
Приведено к модели X01, которая изначально была реализована правильно.

Фазы `awaiting_tie_decision`, `extra_round` и `completed_draw` получили поля
`playerIds`, `roundScores`, `completedPlayerIds`. Поля **необязательные**:
валидаторы принимают и старую форму, потому что у пользователей на устройствах
лежат матчи в прежнем формате.

### Завершение ничьей в X01 (`X01Rules.ts`)

Было: `completeDraw` всегда бросал исключение, `canCompleteDraw` для X01 был
жёстко `false`. Если все игроки промахивались, круги повторялись бесконечно —
проверено на 50 кругах. Единственным выходом было прервать матч, то есть стереть
его результат.

Стало: ничью можно завершить начиная со второго безрезультатного круга. Добавлен
вариант фазы `completed_draw`.

### Знаменатель зачётных средних (`visitStatistics.ts`)

Было: при переборе `physicalDartsUsed` равнялся числу фактически брошенных
дротиков, а `threeDartAverage` считался как `awardedPoints * 3 / physicalDarts`.
При одинаковых 60 зачётных очках перебор первым дротиком давал 45,00, третьим —
30,00. Более грубая ошибка улучшала метрику в полтора раза.

Стало: перебранный подход добавляет в знаменатель зачётных средних три дротика.
Фактическое число бросков по-прежнему используется в бросковых метриках, где оно
честное.

### Доигрывание круга в лимитированном X01

Было: точный выход в ноль завершал матч немедленно, оппонент мог не получить ни
одного подхода. Документация утверждала обратное — что результат определяется
после полного последнего круга.

Стало: в лимитированном формате круг доигрывается, используется результат визита
`tie_pending`, который был объявлен и нигде не применялся. В формате «до победы»
поведение не менялось.

### Фиксация перебора при вводе суммой

Было: сумма, уводящая остаток ниже нуля, отвергалась с текстом «Для завершения
используйте ввод по дротикам». Игрок, который реально перебрал, был вынужден
переключиться на ввод по дротикам и **назвать секторы, которых не видел** — это
противоречило принципу «ввод суммой не создаёт вымышленные сектора».

Стало: перебор суммой фиксируется как перебор. Запрет на завершение матча суммой
сохранён — там действительно нужен последний дротик.

### Прочее по правилам

- `abandon()` на завершённом матче больше не превращает победу в прерванный
  матч, а архивирует его как есть. Раньше это стирало победу из статистики,
  рекордов и серий, оставляя в истории запись со статусом «прерван» и
  проставленным победителем одновременно.
- Начало дополнительного круга стало точкой отмены: раньше отмена перепрыгивала
  через смену фазы и снимала чужой подтверждённый подход.
- `MIN_PLAYERS` и `MAX_PLAYERS` вынесены в домен. Раньше верхняя граница жила
  только в разметке, а домен принимал любое число игроков — матч на девять
  человек создавался, игрался и не переживал перезагрузку.
- В подсказки закрытия добавлен внешний «бул». Это закрыло единственный пробел,
  найденный полным перебором 1080 комбинаций.

## 3. Хранение и синхронизация

### Единственный валидатор матча

Было: `src/domain/match/validation.ts` содержал `isStoredMatch`,
`isSharedMatch`, `isSharedPlayer`, не используемые нигде, — и при этом
дублировал около 90 строк из `IndexedDbRepositories`, расходясь с ним по трём
правилам. А сетевой адаптер импортировал декодер хранилища, чтобы валидировать
ответы сервера.

Стало: полная строгая проверка живёт в домене, её используют и хранилище, и
сеть. Сетевой адаптер применяет `isSharedMatch` — это ровно семантика сетевого
случая. Дубликат удалён.

### Один плохой матч ломал всю компанию

Было: `loadCompany` делал `every(isMatch)` и отвергал **весь снимок**, если хоть
одна запись не проходила проверку. Миграция старых матчей применялась при чтении
локальной истории, но не здесь. Воспроизведение: один матч на сервере без
`state.outRule` делал компанию недоступной для всех устройств целиком, включая
корректные матчи и список игроков.

Стало: записи мигрируются и отбраковываются поштучно, наружу отдаётся число
пропущенных. Так же, как это изначально было сделано для локальной истории.

### Отравленное соединение с базой

Было: `database ??= openDB(...)` кэшировал в том числе **отклонённый** промис.
Одна ошибка — приватный режим Safari, квота, блокировка обновления другой
вкладкой — выводила хранилище из строя до конца жизни вкладки, даже после
устранения причины.

Стало: отказ сбрасывает кэш. Добавлены обработчики `blocked`, `blocking`,
`terminated` с понятными сообщениями.

### Многовкладочность

Было: `saveActive` безусловно перезаписывал полный снимок. Две вкладки с одним
матчем затирали прогресс друг друга без следа: вкладка, висящая на экране
«Продолжить матч», одним введённым дротиком стирала все подходы, введённые в
другой.

Стало: в конверт добавлена монотонная ревизия, запись идёт в транзакции со
сверкой, конфликт отдаётся типизированной ошибкой. Изменения вещаются через
`BroadcastChannel`. Ревизия отслеживается внутри репозитория, поэтому сигнатуры
портов и `GameSession` не изменились.

### Схема IndexedDB, версия 2

Было: стор `meta` использовался как свалка для шести видов сущностей, поэтому
список компаний и матчей читался полным сканом, а слияние удалённых данных
делало отдельное чтение на каждый ключ — 502 чтения на 501 запись. У стора
матчей не было ни одного индекса, вся история грузилась при каждом старте.

Стало: отдельные стор-ы для компаний, их игроков, их матчей и надгробий; индекс
по дате создания матча. Чтение идёт по индексам и курсорам. Написана миграция с
версии 1, идемпотентная, выполняемая внутри транзакции обновления, покрытая
тестом на все шесть видов ключей.

### Резервная копия

Было: в копию не попадали компании, кэш их игроков, очередь неотправленных
матчей, шаблоны настройки и токен активного матча. Восстановление на новом
устройстве теряло доступ к компании, а старые ключи от предыдущего владельца
устройства не очищались.

Стало: версия копии 2, включает все перечисленное; восстановление очищает старые
данные; копии версии 1 по-прежнему читаются.

### Удаление матча компании

Было: матч компании хранился локально дважды, а удаление затрагивало только
серверную сторону и щадило записи в состоянии «ожидает отправки». Удалённый
матч заливался обратно при следующей синхронизации.

Стало: удаление симметричное, с надгробием, чтобы слияние не воскрешало запись.
Локальная копия в истории устройства сохраняется намеренно — она должна
переживать выход из компании.

### Сетевой клиент и синхронизация

Было: все коды ответа, кроме 404, схлопывались в одно сообщение «Не удалось
связаться с компанией»; таймаутов не было, зависший запрос висел бесконечно и
приложение выглядело зависшим; не-JSON ответ от промежуточного прокси
пробрасывал сырое английское исключение в интерфейс; неустранимые ошибки вроде
превышения размера переотправлялись бесконечно; выгрузка шла строго
последовательно — 50 матчей на мобильной сети занимали от 15 до 40 секунд;
операции с игроками читали и перезаписывали весь массив, теряя обновления при
конкуренции.

Стало: типизированная ошибка с кодом и признаком неустранимости; таймаут 10
секунд через `AbortController`; повторы с разбросом только для чтения;
безопасный разбор ответа; состояние «отклонено» с сохранённой причиной без
переотправки; экспоненциальная задержка для устранимых; пул на три параллельные
выгрузки; защита от повторного входа; операции с игроками — в одной транзакции и
через общую очередь; предпроверка размера тела перед отправкой.

### Откат деплоя

Было: список поддерживаемых версий схемы был перечислением, поэтому откат на
старую версию клиента приводил к исключению и предложению стереть всю историю.

Стало: версия из будущего не роняет загрузку — активный матч просто не
восстанавливается, история не трогается, наружу отдаётся признак причины.

## 4. Интерфейс и PWA

### Принудительная перезагрузка при каждом деплое

Было: `registerType: 'autoUpdate'` вместе с `skipWaiting` и обработчиком
`activate`, вызывавшим `client.navigate(client.url)` для каждого открытого окна
без единого условия. Подтверждено по собранному `dist/sw.js`. Любой деплой
выбрасывал игрока из матча посреди подхода, стек отмены сокращался с двадцати
точек до одной, состояние экрана терялось.

Стало: обновление применяется только по нажатию пользователя. Появилась плашка
«Доступна новая версия», во время активного матча она честно предупреждает о
последствиях. `sw-update.js` больше не навигирует окна, в нём остался только
обработчик сообщения. Тест PWA переписан с грепа по собранным файлам на проверку
реального поведения.

### Кнопка, стирающая всё

Было: при **любой** ошибке показывался красный блок с кнопкой, удаляющей всю
базу без подтверждения. Туда попадала и обычная потеря связи: открытие
ссылки-приглашения офлайн давало пользователю английское `Failed to fetch` рядом
с кнопкой «решения». Все остальные разрушительные действия в приложении
подтверждения спрашивали.

Стало: отказ хранилища и сетевая ошибка разведены по разным каналам. Сетевая
показывается обычным уведомлением с кнопкой «Повторить». Стирание проводится

## Чего делать не надо

- **Не переписывать архитектуру.** Слои, порты и доменная модель сделаны
  правильно, аудит это подтвердил отдельно. Границы проверяются исполняемым
  тестом `tests/architecture.test.ts` — если он покраснел, нарушена граница
  слоя, а не устарел тест.
- **Не добавлять слои и классы там, где сейчас чистые функции.** Текущее решение
  лучше.
- **Не ужесточать валидаторы фаз**, не проверив, что матчи в старом формате
  продолжают загружаться. У пользователей на устройствах лежат реальные записи.
- **Не менять формат ответов сервера** без учёта того, что старые версии
  приложения остаются на устройствах.
- **Не возвращать `skipWaiting` в автозапуск service worker.** Именно из-за него
  деплой выбрасывал игроков из матча.
- **Не добавлять зависимости без необходимости.** У сервера их ноль, и это
  ценное свойство: на машине не нужен ни `npm ci`, ни `node_modules`.
